[上一篇]({% link _AI/2026-04-16-reading_about_vllm.md %})基于 v0.18 走完了 vLLM V1 从 HTTP 请求到 token 输出的全链路，第六节只用一张表列了 Model Runner V2（MRV2）和旧 Runner 的差别。半年过去，MRV2 在 v0.29 成为默认实现，`main` 分支已经删掉了旧 Runner。

这篇只做一件事：**把上一篇的 64 路视频例子原样交给两代 Runner**，看每一步怎么执行、要搬多少数据、哪些工作消失了。

> **版本**：MRV1 取 `v0.18.1` 的 [`gpu_model_runner.py`][old-runner]，MRV2 取 `main@3a104103ac`（v0.34.0 开发周期）的 [`vllm/v1/worker/gpu/`][mrv2-dir]，设计动机见官方 [MRV2 设计文档][mrv2]。
>
> **名字**：MRV1 和 MRV2 都运行在 vLLM V1 引擎里，这里的 V1、V2 是 Model Runner 的版本，与引擎版本无关。

## 太长不看：五个改动，一条主线

{% include figure.liquid loading="eager" path="assets/img/AI/reading-vllm-v2/mrv2-scope.svg" class="img-fluid rounded z-depth-1" zoomable=true alt="MRV2 只替换 Worker 中的 Model Runner，Scheduler 和接口保持不变" %}

Scheduler、KV Cache 管理、进程拓扑都没变。两代 Runner 收到同一份 `SchedulerOutput`，交回同一种 `ModelRunnerOutput`，变化全部在 Worker 内部。下表的数字都来自后文的例子，计算方法见[附录](#附录计算口径与对上一篇的修正)。

| #   | 改了什么         | MRV1 怎么做                                                                                                      | MRV2 怎么做                                                          | 例子中省掉了什么                                                         |
| --- | ---------------- | ---------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| ①   | **持久批次**     | 状态表的行号就是本步 batch 顺序。请求进出要 `condense` 或 `swap_states` 搬整行，还要 `CachedRequestState` 做备份 | 每个请求在生命周期内固定占一个槽，本步顺序另用 `idx_mapping` 表示    | R1 退出、R33 加入：两整行互换约 **544 KB → 0**（后端要求 decode 在前时） |
| ②   | **输入在哪准备** | CPU 用 NumPy 逐 token 计算 `positions`、`slot_mapping`，gather `input_ids`，再拷到 GPU                           | Triton kernel 按 `idx_mapping` 在 GPU 上直接生成                     | 第 3 步：CPU 逐 token 生成的约 **4.1 万个数（288 KB）→ 0**               |
| ③   | **大表怎么更新** | 每步把本步请求的**整行**块表拷到 GPU                                                                             | 块表常驻 GPU，`StagedWriteTensor` 只上传新增的块 ID                  | 32 路纯 decode：每步 **256 KB → 几十字节**                               |
| ④   | **异步执行**     | 后来才补上异步支持：复用 pinned 缓冲靠 barrier，上一步 token 先填 -1 再 scatter，投机解码要等接受数拷回 CPU      | 采样 token 和计算进度直接写回 GPU 上的槽位，下一步 kernel 按槽号读取 | 投机解码每步一次 `event.synchronize()` → **0**                           |
| ⑤   | **采样器**       | softmax 得到概率，再生成一张同样大小的指数噪声表                                                                 | Triton Gumbel-Max：在寄存器里生成噪声，直接 argmax                   | 32 行 × 151,936 词表的两张临时表约 **37 MB → 0**                         |

另外，Qwen3-VL 的 M-RoPE、多模态 embedding 这类模型差异收进了 `ModelState` 接口，CUDA Graph 改由 `CudaGraphManager` 显式管理，`dummy_run` 直接复用 `execute_model`。

这五点出自同一个设计决定：**把“请求状态”和“本步输入”拆开。**

{% include figure.liquid loading="eager" path="assets/img/AI/reading-vllm-v2/mrv2-core-idea.svg" class="img-fluid rounded z-depth-1" zoomable=true alt="MRV1 的持久状态就是模型输入；MRV2 的状态放在固定槽位，每步按 idx_mapping gather 出输入" %}

这几步是连起来的：

1. 状态有了**稳定的槽号**，请求进出就不必搬动别的请求（①）。
2. 槽号稳定后，状态可以**常驻 GPU**，本步输入交给 kernel 按映射 gather（②③）。
3. 输入在 GPU 上生成，CPU 就**不需要知道** GPU 刚采出的 token 和接受数，异步执行时也就不用停下来等（④）。

后文按这个顺序展开。

## 读前先认识几个名词

| 名词                         | 含义                                                                                                           | 在哪                                        |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------- | ------------------------------------------- |
| 持久批次（Persistent Batch） | 跨 step 保留的请求状态：token 历史、已算位置数、块表、采样参数。相邻两步的请求大多相同，复用它们比每步重建便宜 | 两代都有                                    |
| 槽（slot / `req_idx`）       | MRV2 给每个请求分配的固定行号，从请求加入用到它结束或被抢占                                                    | [`RequestState`][states]                    |
| `idx_mapping`                | 本步第 i 个请求的状态在哪个槽，例如 `[31, 30, 28, 29]`                                                         | [`gather_batch_req_state()`][runner-gather] |
| `query_start_loc`            | 所有请求的输入拼成一条扁平序列，它记录每个请求的起止下标                                                       | 两代都有                                    |
| pinned 内存 / UVA            | pinned 是页锁定的主机内存，可以异步拷到 GPU；UVA（统一虚拟寻址）让 GPU kernel 直接读写这块内存                 | [`UvaBufferPool`][uva-pool]                 |
| staged write                 | 先在 CPU 上记下“第几行、从第几列起、写哪些值”，再打包上传，由一个 kernel 写入 GPU 上的大表                     | [`StagedWriteTensor`][staged]               |

## 一、例子：同一份调度，交给两代 Runner

沿用上一篇第 5.6 节的场景：Qwen3-VL 同时处理 64 路视频理解请求。

| 参数                     | 取值                                          | 说明                                                 |
| ------------------------ | --------------------------------------------- | ---------------------------------------------------- |
| 模型                     | Qwen3-VL-8B-Instruct                          | M-RoPE 有 3 个位置通道，词表 151,936                 |
| prompt 长度              | 7,000 token / 请求                            | 视频占位 + 文本，沿用上一篇的整数值                  |
| 输出长度                 | 200 token / 请求                              | 上一篇写 R1 在第 200 步左右结束                      |
| `max_num_batched_tokens` | 8,192                                         | 每步 token 预算                                      |
| `max_num_seqs`           | 32                                            | 最多 32 个活跃请求，也是 MRV2 的槽数                 |
| `max_model_len`          | 32,768                                        | **本文假设**。决定 MRV1 token 表和两代块表一行有多宽 |
| `block_size`             | 16                                            | 块表一行 32,768 / 16 = 2,048 项 = 8 KB               |
| 其他                     | 关闭 prefix cache 和投机解码，KV 充足、无抢占 | 第五节讨论投机解码                                   |

Scheduler 没有变，所以**两代 Runner 收到的每一步任务完全相同**。按源码规则把 428 步全部推演一遍，结果如下：

{% include figure.liquid loading="eager" path="assets/img/AI/reading-vllm-v2/schedule-timeline.svg" class="img-fluid rounded z-depth-1" zoomable=true alt="64 路请求的调度：前 28 步阶梯接入，29–200 步 32 路纯 decode，201–229 步轮替，之后 decode 到结束" %}

| 调度步                             | Scheduler 下发的工作                                                             |      token 数 | 活跃请求 |
| ---------------------------------- | -------------------------------------------------------------------------------- | ------------: | -------: |
| 1                                  | R1 prefill 7,000 · R2 prefill 1,192                                              |         8,192 |        2 |
| 2                                  | R1 decode 1 · R2 prefill 5,808 · R3 prefill 2,383                                |         8,192 |        3 |
| **3（镜头 A）**                    | R1、R2 各 decode 1 · R3 prefill 4,617 · R4 prefill 3,573                         |         8,192 |        4 |
| 4 – 28                             | 阶梯式接入，第 27 步 32 个槽占满                                                 |         8,192 |   5 → 32 |
| **29 – 200（镜头 B 取第 100 步）** | 32 路纯 decode                                                                   |            32 |       32 |
| **201（镜头 C）**                  | R1 在第 200 步生成完 200 个 token 后退出；R2–R32 各 decode 1 · R33 prefill 7,000 |         7,031 |       32 |
| 202 – 229                          | 每步约一出一进                                                                   | 7,031 – 8,192 |       32 |
| 230 – 428                          | R33–R64 decode 到结束                                                            |          ≤ 32 |   32 → 0 |

R1、R2、R3、R4 在第 1、2、3 步采出的 token 分别记作 `a1 a2 a3`、`b1 b2`、`c1`。推演按同步调度进行，也就是 Scheduler 拿到第 N 步的输出后再调度第 N+1 步；开启异步调度时 R1 的退出会晚一步被看到，不影响下面的对比。

三个镜头对应 Runner 最常遇到的三种情况：

- **镜头 A · 第 3 步**：decode 和 prefill 混在一起，用来看输入怎么准备。
- **镜头 B · 第 100 步**：稳态纯 decode，用来看每步的固定开销。
- **镜头 C · 第 201 步**：一个请求退出、一个请求加入，用来看持久批次怎么维护。

## 二、一步之内，两代 Runner 各做了什么

{% include figure.liquid loading="eager" path="assets/img/AI/reading-vllm-v2/runner-pipeline.svg" class="img-fluid rounded z-depth-1" zoomable=true alt="MRV1 与 MRV2 的单步执行流程对照，标出 CPU、GPU 和同步点" %}

两代都把一步拆成 `execute_model()`（更新状态、准备输入、forward）和 `sample_tokens()`（采样、收尾）两次调用。差别在图中的颜色：MRV1 有两处要等 GPU 的同步点（橙色），准备输入主要靠 CPU（蓝色）；MRV2 的准备工作大多搬到了 GPU（绿色），有三处工作直接消失（虚线）。

| 阶段         | MRV1                                                                                                                                       | MRV2                                                                                                                                         |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 更新请求状态 | [`_update_states()`][old-update]：维护 `self.requests`（`CachedRequestState`）和 `InputBatch`，做 `condense()`，按 attention 后端重排      | [`finish_requests()`][runner-finish] / [`add_requests()`][runner-add] / [`update_requests()`][runner-update]：只占槽、还槽，所有写入先 stage |
| 决定本步顺序 | `InputBatch` 的行顺序就是 batch 顺序                                                                                                       | [`gather_batch_req_state()`][runner-gather]：[排序][runner-sort]后得到 `idx_mapping`                                                         |
| 准备输入     | [`_prepare_inputs()`][old-prep]：NumPy 计算后逐个 `copy_to_gpu()`；[`_prepare_input_ids()`][old-input-ids] 再把上一步的 token scatter 进去 | [`prepare_inputs()`][runner-inputs] + [`prepare_attn()`][runner-attn]：Triton kernel 在 GPU 上生成                                           |
| 采样         | PyTorch softmax + 指数噪声                                                                                                                 | Triton Gumbel-Max                                                                                                                            |
| 收尾         | [`_bookkeeping_sync()`][old-bookkeeping]：CPU 为还没拷回的 token 写 -1 占位                                                                | [`postprocess_sampled()`][runner-postprocess]：`post_update` kernel 把结果写回槽位                                                           |

## 三、改动①：持久批次，从“行号即顺序”到“固定槽位”

**镜头 C · 第 201 步。** 32 个活跃请求中，R1 生成完毕退出，R33 加入并一次性 prefill 7,000 个 token，其余 31 个继续 decode。

{% include figure.liquid loading="eager" path="assets/img/AI/reading-vllm-v2/slots-vs-rows.svg" class="img-fluid rounded z-depth-1" zoomable=true alt="MRV1 交换 R32 和 R33 的整行状态；MRV2 让 R33 复用 R1 的槽，已有请求不动" %}

### MRV1：行号就是本步的位置

`InputBatch` 是一组以行为单位的 CPU 数组。行号同时承担两件事：标识请求的状态，以及决定请求在本步扁平输入里的位置。第 201 步的处理过程：

1. [`remove_request("R1")`][old-update] 空出行 0。
2. R33 用 `add_request()` 填进**最小的空行**，也就是行 0，并写入 7,000 个 prompt token、438 个块 ID 和采样参数。
3. 空行已经填满，`condense()` 不用动。
4. `_may_reorder_batch()`：如果 attention 后端要求 decode 在前（FlashInfer、MLA 等），行 0 的 R33 是 prefill、行 31 的 R32 是 decode，于是执行 [`swap_states(0, 31)`][old-swap]。

`swap_states` 要交换的不只是请求 ID：

| 被交换的数据                                                                     | 一行多大 | 交换时实际拷贝                   |
| -------------------------------------------------------------------------------- | -------- | -------------------------------- |
| [`token_ids_cpu`][old-token-table]（int32 × `max_model_len`）                    | 128 KB   | 临时副本 + 两次整行赋值 = 384 KB |
| `is_token_ids`（bool × `max_model_len`）                                         | 32 KB    | 花式索引读两行 + 写两行 = 128 KB |
| 块表行（int32 × 2,048）                                                          | 8 KB     | 同上 = 32 KB                     |
| 十余个标量数组（进度、温度、top-p、惩罚项…），以及 generators、bad_words 等 dict | —        | 二十多次 Python 层交换           |
| **合计**                                                                         |          | **约 544 KB 内存拷贝**           |

R32 本身什么都没变，只是因为 R33 进来，它的整行状态就从行 31 搬到了行 0。如果 R1 退出时没有新请求补位，`condense()` 会把最后一行搬进空洞，同样要复制有效 token、块表和全部标量。

### MRV2：槽号固定，顺序另给

[`RequestState`][states] 预分配 `max_num_reqs` 行（本例为 32），用一个空闲栈 `free_indices` 分配。第 1 步 R1 先拿到槽 31，R2 拿到槽 30，以此类推，R32 拿到槽 0。第 201 步的处理过程：

1. [`finish_requests()`][runner-finish]：R1 的槽 31 压回空闲栈。
2. [`add_requests()`][runner-add]：R33 从栈顶取回槽 31，prompt 和块 ID 以 staged write 记下，随后由一个 kernel 写进槽 31。
3. [`sort_batch_req_ids()`][runner-sort]：decode 在前，其余按本步 token 数升序，得到 `[R2, …, R32, R33]` 和 `idx_mapping = [30, 29, …, 0, 31]`。

**已有请求的状态一个字节都不动。** 其他生命周期事件也一样简单：

| 事件                             | MRV1                                                                   | MRV2                                                |
| -------------------------------- | ---------------------------------------------------------------------- | --------------------------------------------------- |
| 请求退出，有新请求补位           | 新请求填进空行，后端要求时整行 swap                                    | 新请求复用空出的槽                                  |
| 请求退出，无人补位               | `condense()` 把最后一行搬进空洞                                        | 只归还槽                                            |
| 请求本步没被调度（例如预算不够） | 移出 `InputBatch`，状态暂存在 `CachedRequestState`，下次重新写回一整行 | 槽保留，本步 `idx_mapping` 跳过它                   |
| 被抢占后恢复                     | 走 resumed 路径，从 `CachedRequestState` 重建                          | 抢占视为结束，恢复时当作新请求重新 `add_requests()` |
| 需要备份吗                       | 需要 `CachedRequestState`，因为行会被覆盖或移动                        | 不需要，槽就是唯一的数据源                          |

后端差异也要注意：Qwen3-VL 在 Hopper 上默认用 FlashAttention，不要求 decode 在前，MRV1 会跳过第 4 步，本步顺序变成 `[R33, R2, …, R32]`。MRV2 不管什么后端都统一排序，而且排序只改 `idx_mapping`，不搬数据。

**为什么稳定的槽号这么重要？** 在 MRV1 里，同一个请求的行号会变，比如 R32 从行 31 变成行 0。凡是按行号索引的 GPU 状态，每步都要先在 CPU 上算一遍“上一步在第几行、这一步在第几行”的对应关系，第五节的 `prev_req_id_to_index` 就是例子。MRV2 中 R32 一直在槽 0，`last_sampled_tokens[0]`、`num_computed_tokens[0]`、块表第 0 行可以长期放在 GPU 上，下一步 kernel 直接按槽号读取。后面三个改动都建立在这一点上。

## 四、改动②③：输入在 GPU 上生成，大表只传增量

### 镜头 A · 第 3 步：8,192 个输入 token 从哪里来

第 3 步有 4 个请求：R1、R2 各 decode 1 个 token，R3 续算 prefill 的后 4,617 个 token，R4 算 prefill 的前 3,573 个 token。

{% include figure.liquid loading="eager" path="assets/img/AI/reading-vllm-v2/step3-inputs.svg" class="img-fluid rounded z-depth-1" zoomable=true alt="第 3 步 MRV2 按 idx_mapping 从槽位读取 a2、b1 和 prompt 片段，生成扁平输入及元数据" %}

MRV2 先排序：R1、R2 是 decode 排在前面，R4（3,573）比 R3（4,617）短，排在 R3 前面，所以顺序是 `[R1, R2, R4, R3]`，`idx_mapping = [31, 30, 28, 29]`。**CPU 上只算两样东西**：`idx_mapping`，以及对 `[1, 1, 3573, 4617]` 求前缀和得到的 `query_start_loc = [0, 1, 2, 3575, 8192]`。其余数据都由 GPU kernel 生成：

| 字段           | 第 3 步的值                                | 由哪个 kernel 生成                                                                                                                                                                  |
| -------------- | ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `input_ids`    | `[a2 · b1 · R4 p0…p3572 · R3 p2383…p6999]` | [`combine_sampled_and_draft_tokens`][k-combine] 从 `last_sampled_tokens[31]`、`[30]` 取 a2、b1；[`prepare_prefill_inputs`][k-prefill] 从 `all_token_ids[28]`、`[29]` 取 prompt 片段 |
| `positions`    | `[7001 · 7000 · 0…3572 · 2383…6999]`       | [`prepare_pos_seq_lens`][k-pos]：已算位置数 + 偏移。Qwen3-VL 的 3 通道 M-RoPE 位置由 [`RopeState`][rope] 的 kernel 读取预存的 prefill 位置                                          |
| `seq_lens`     | `[7002, 7001, 3573, 7000]`                 | 同上：已算位置数 + 本步 query 长度                                                                                                                                                  |
| 块表           | 4 行                                       | [`gather_block_tables`][bt-gather]：按槽号从常驻 GPU 的块表复制                                                                                                                     |
| `slot_mapping` | 8,192 个 KV slot                           | [`compute_slot_mappings`][bt-slot]：查块表 + positions                                                                                                                              |
| logits 位置    | `[0, 1, 3574, 8191]`                       | 每个请求最后一个输入位置                                                                                                                                                            |

采样后，R1 得到 `a3`，R2 得到 `b2`，R3 完成 prompt 得到首个 token `c1`；R4 的 prompt 还没算完，本步不出 token（`num_sampled = 0`）。

**同一步的 MRV1**：行顺序是 `[R1, R2, R3, R4]`，`query_start_loc = [0, 1, 2, 4619, 8192]`。CPU 先用 `np.repeat` 展开出每个 token 属于哪一行，再算 positions，用 `index_select` 从 `token_ids_cpu` 取出 8,192 个 token；[`_calc_mrope_positions()`][old-mrope] 按请求循环拷贝 M-RoPE 位置；接着用 NumPy 查块表算 `slot_mapping`，最后逐个数组拷到 GPU。R1、R2 的 a2、b1 在异步调度下还没回到 CPU，只能先填 -1，等上了 GPU 再 scatter 成真实 token（见第五节）。

### 两代每步上传多少数据

把每步“CPU 要算好、再拷给 GPU”的数据按字段拆开，每格写成 **MRV1 → MRV2**（MRV1 中 `slot_mapping`、M-RoPE positions 是 int64，`input_ids`、块表是 int32）：

| 字段                                            | 镜头 A（4 请求，8,192 token）            | 镜头 B（32 请求，32 token）             |
| ----------------------------------------------- | ---------------------------------------- | --------------------------------------- |
| 块表                                            | 4 整行 32 KB → 新增 513 个块 ID，约 2 KB | 32 整行 **256 KB** → 偶尔追加，几十字节 |
| M-RoPE positions                                | 3 × 8,192 × 8 B = 192 KB → 0（GPU 生成） | 768 B → 0                               |
| `slot_mapping`                                  | 8,192 × 8 B = 64 KB → 0（GPU 生成）      | 256 B → 0                               |
| `input_ids`                                     | 8,192 × 4 B = 32 KB → 0（GPU 读槽位）    | 128 B → 0                               |
| `query_start_loc`、`seq_lens`、`idx_mapping` 等 | 0.3 KB → 0.2 KB                          | 0.3 KB → 0.4 KB                         |
| **合计**                                        | **320 KB → 2.2 KB**                      | **257 KB → 0.4 KB**                     |

块表一项的差别来自[`commit_block_table(num_reqs)`][old-commit-bt]：MRV1 每一步都把本步请求的**整行**拷上 GPU，行宽由 `max_model_len` 决定，和请求实际用了多少块无关。MRV2 的块表常驻 GPU，[`append_block_ids()`][bt-append] 只 stage 新增的块 ID。镜头 A 中 R3 从 149 块增长到 438 块（+289），R4 新分配 224 块；镜头 B 中每个请求每 16 个 token 才跨过一次块边界，32 个请求平均每步不到 2 个新块。

整个 64 路任务累计下来，MRV1 约上传 **116 MB**，MRV2 约 **0.27 MB**。

有两点要说清楚，免得把这组数字读偏：

1. **prompt 内容本身仍要进入 GPU。** MRV2 默认把 `all_token_ids` 和 M-RoPE 的 prefill 位置放在 UVA 主机内存里以节省显存，由 kernel 直接读取，全程约 6.8 MB；MRV1 对应的部分就是上表中 prefill 阶段的 `input_ids` 和 positions。区别在于 MRV2 这一步不需要 CPU 逐元素 gather，位置也从 int64 缩成了 int32。
2. **字节本身不是瓶颈，CPU 时间才是。** 257 KB 在 PCIe 上只要十几微秒。真正的开销是 MRV1 每步要在 Python/NumPy 里生成这些数组，外加多处按请求的 Python 循环（`_update_states`、`_calc_mrope_positions`、`_prepare_input_ids`、`_bookkeeping_sync`）。GPU 一步只要几毫秒时（小模型、纯 decode、大 batch），CPU 准备时间就会成为瓶颈。官方专门挑了 Qwen3-0.6B / 1×GB200 来放大这部分开销，MRV2 的输出吞吐从 16K tok/s 提到 25K tok/s（**+56%**）[[MRV2 发布文章]][mrv2-blog]。

块表的这项差别还会随配置放大。块表一行有 `max_model_len / block_size` 项：128K 上下文时一行 32 KB，256 个并发请求的纯 decode 步里，MRV1 每步要上传 8 MB 块表，MRV2 仍然只传增量。

### StagedWriteTensor：增量是怎么写进去的

块表、`all_token_ids`、`num_computed_tokens` 这类大表都用 [`StagedWriteTensor`][staged]：

```python
# 第 3 步：R3 追加 289 个块，R4 是新请求，从第 0 列写 224 个块
# stage_write 只记账，不拷贝
block_table.stage_write(row=29, start=149, value=r3_new_blocks)
block_table.stage_write(row=28, start=0,   value=r4_blocks)
block_table.apply_write()
# ① 把行号 [29, 28]、起始列 [149, 0]、长度前缀和 [289, 513]
#    和 513 个块 ID 打包进一块轮转的 pinned 缓冲（GPU 经 UVA 直接读）
# ② 启动一个 Triton kernel，按“哪一行、从第几列起”写进 GPU 上的大表
```

无论这一步有多少个请求改了多少行，都只需要一次打包和一次 kernel launch。

## 五、改动④：异步优先，采样结果留在 GPU

开启异步调度后，CPU 要在 GPU 跑第 N 步的同时准备第 N+1 步。问题是，准备第 3 步时，R1 的 `a2` 和 R2 的 `b1` 刚在 GPU 上采出来，CPU 还看不到。

### MRV1：先占位、再修补，必要时停下来等

1. 第 2 步收尾时，[`_bookkeeping_sync()`][old-bookkeeping] 往 `token_ids_cpu` 里写 `-1` 占位，表示这个 token 还没拷回来。
2. 第 3 步 `_prepare_inputs()` 在 CPU 上 gather 出 `[-1, -1, R3 片段, R4 片段]`，拷到 GPU。
3. [`_prepare_input_ids()`][old-input-ids] 按 `prev_req_id_to_index` 找出“上一步第几行、这一步扁平下标是多少”。顺序没变时直接拷贝；顺序变了就要在 CPU 上构造两组索引，拷到 GPU 后再 `scatter_`。
4. 输入用的 pinned 缓冲每步复用，CPU 改写前必须确认上一步的异步拷贝已经读完。[`synchronize_input_prep()`][old-barrier] 等的就是这件事。稳态下它通常很快返回，麻烦在于所有写这些缓冲的代码都必须放在这个 barrier 里，漏放一处就是竞态，代码的组织方式也被它限制住了。
5. **投机解码时情况更糟**：CPU 要知道上一步接受了几个 draft token，才能修正 `num_computed_tokens`。[`_get_valid_sampled_token_count()`][old-valid-count] 每步都要 `event.synchronize()`，CPU 只能等 GPU 拒绝采样完成。

### MRV2：结果写回槽位，下一步按槽读取

1. 第 2 步采样后，[`post_update`][k-post] kernel 在 GPU 上执行 `last_sampled_tokens[31] = a2`、`last_sampled_tokens[30] = b1`，把 token 追加进 `all_token_ids`，再执行 `num_computed_tokens[槽] += query_len - num_rejected`。
2. 第 3 步的 [`combine_sampled_and_draft_tokens`][k-combine] 按 `idx_mapping` 读 `last_sampled_tokens[31]`、`[30]`，填进 `input_ids[0]`、`[1]`。**CPU 从头到尾不需要知道 a2、b1 是什么。**
3. 投机解码时，接受和拒绝了几个 token 都在 GPU 上修正。CPU 只保留一个乐观上界 `num_computed_tokens_np`，用来估计 buffer 大小。
4. CPU 交给 GPU 的数据要么是每步新建的快照（[`async_tensor_h2d`][async-h2d] 会先复制进一块新的 pinned 缓冲），要么来自轮转的 [`UvaBufferPool`][uva-pool]（深度不小于 batch queue 的在途步数）。CPU 不会去改一块还有在途读者的内存，所以不需要 barrier。
5. 输出由 [`AsyncOutput`][async-output] 在独立的 copy stream 上拷回，只有 CPU 真正要消费结果时才等这个 event。

{% include figure.liquid loading="eager" path="assets/img/AI/reading-vllm-v2/async-timeline.svg" class="img-fluid rounded z-depth-1" zoomable=true alt="投机解码下，MRV1 的 CPU 要等接受数才能准备下一步，GPU 出现空闲；MRV2 的 CPU 提前提交，GPU 连续执行" %}

| 同步点               | MRV1                                          | MRV2                                      |
| -------------------- | --------------------------------------------- | ----------------------------------------- |
| 复用输入 pinned 缓冲 | barrier：`prepare_inputs_event.synchronize()` | 每步新快照或轮转缓冲池，不需要等          |
| 上一步采样出的 token | CPU 写 -1 占位，GPU 按 CPU 构造的索引 scatter | kernel 按槽号直接读 `last_sampled_tokens` |
| 投机解码的接受数     | 每步 `event.synchronize()` 拷回 CPU           | GPU 内修正，CPU 不等                      |
| 输出拷回 CPU         | copy stream + event                           | copy stream + event（`AsyncOutput`）      |

举个投机解码的例子：R2 的 draft 是 `x, y, z`，验证时接受 `x`、拒绝 `y`，并在被拒位置采出 `w`，这一步真实输出 `[x, w]`。MRV1 要先把“接受 1 个”拷回 CPU，才能算对 R2 的进度；MRV2 由 kernel 直接把进度减去被拒绝的 token 数，下一步从 `last_sampled_tokens` 读到 `w` 接着算。官方在 GLM-4.7-FP8 + MTP / 4×GB200 上测得 TPOT 降低 **6.3%**，原因就是去掉了这类同步点 [[MRV2 发布文章]][mrv2-blog]。

## 六、改动⑤：Triton 采样器

还是**镜头 B**：32 个请求都在 decode，每个请求一行 logits，词表 151,936。

|                             | MRV1（[`Sampler`][old-sampler]）                                                                                                                 | MRV2（[`Sampler`][sampler]）                                                                        |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------- |
| 随机采样                    | `softmax` 得到 probs [32, V] fp32；[`random_sample`][old-random-sample] 再用 `q.exponential_()` 生成同样大小的噪声 q；最后取 `argmax(probs / q)` | [Gumbel-Max][gumbel]：kernel 内按 (seed, 位置, token) 哈希出噪声 g，直接取 `argmax(logits / T + g)` |
| 额外的 [B, V] 临时张量      | probs 与 q 两张，32 × 151,936 × 4 B × 2 ≈ **37 MB**                                                                                              | **0**，噪声只在寄存器里存在                                                                         |
| 指定 seed 的请求            | 每个请求一个 `torch.Generator`，Python 循环逐个生成噪声                                                                                          | 无状态 RNG：seed 和位置是 kernel 输入，一次 launch 处理全部请求                                     |
| top-k logprobs              | 先对全词表 `log_softmax`（又一张 [B, V]），再取 top-k                                                                                            | [先在 logits 上取 top-k][logprob]，算出 logsumexp 后只写 k 个值                                     |
| 投机解码一个请求多行 logits | 把采样参数按行展开                                                                                                                               | `expanded_idx_mapping` 让多行共用一个槽的参数                                                       |

两种随机采样在数学上等价：对 Exp(1) 噪声 q 取 `argmax(p / q)`，和对 Gumbel 噪声 g 取 `argmax(log p + g)`，得到的都是按 p 分布的样本。差别只在于 MRV1 要先把概率表和噪声表都落到显存里。临时显存是 `2 × B × V × 4 B`：B = 32 时约 37 MB，B = 1,024 时约 1.2 GB。

无状态 RNG 还省掉了一类记账工作。MRV1 中 chunked prefill 的中间块也会采样再丢弃（第 3 步的 R4 就是这样），为了不打乱指定 seed 的随机序列，`_bookkeeping_sync()` 要把这些请求的 Generator offset 拨回去。MRV2 的噪声只由 seed、位置和 token 决定，没有需要回拨的状态。

## 七、模块化：Qwen3-VL 的特殊逻辑放在哪

MRV1 把模型相关的逻辑直接写在 6,720 行的 `gpu_model_runner.py` 里，例如 `_init_mrope_positions()`、`_calc_mrope_positions()`、`_execute_mm_encoder()`、`_gather_mm_embeddings()`。MRV2 抽出 [`ModelState`][model-state] 接口，公共 Runner 只调用接口：

| `ModelState` 方法                         | 第 3 步对 Qwen3-VL 做了什么                                                                        |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `add_request()` / `apply_staged_writes()` | R4 加入时算出整段 prompt 的 3 通道 M-RoPE 位置，stage 进 `RopeState`                               |
| `prepare_inputs_embeds()`                 | 对本步调度到的视频项跑视觉 encoder，或从 encoder cache 取出 embedding，按 placeholder 位置放进输入 |
| `prepare_inputs()`                        | 用 kernel 按 `idx_mapping` 生成本步的 M-RoPE positions                                             |
| `prepare_attn()`                          | 构造 attention metadata                                                                            |
| `postprocess_state()`                     | 采样后更新模型私有状态（例如 Mamba 混合模型）                                                      |

其他模块化改动：

| 主题        | MRV1                                                                             | MRV2                                                                                                                          |
| ----------- | -------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 代码组织    | `gpu_model_runner.py` 单文件 6,720 行，`gpu_input_batch.py` 1,036 行             | `vllm/v1/worker/gpu/` 下 117 个文件，按 sample / spec_decode / mm / model_states 等拆分；最大的 `model_runner.py` 有 2,597 行 |
| `dummy_run` | 一个函数同时负责 profiling、CUDA Graph 捕获、warmup、DP 空跑，和真实路径容易分叉 | [`_dummy_run()`][dummy-run] 调用 `execute_model(dummy_run=True)`，与真实 forward 共用一条路径；graph 捕获另走专门流程         |
| CUDA Graph  | 隐式管理，难以推断哪一步走了哪种 graph                                           | [`CudaGraphManager`][cg-manager] 显式 capture 和 replay；还能把多步 draft forward 捕获进同一张 graph                          |

## 八、总结：一张表看完 MRV1 → MRV2

| 维度         | MRV1（v0.18.1）                                           | MRV2（main）                            | 本文例子中的差别                                                      |
| ------------ | --------------------------------------------------------- | --------------------------------------- | --------------------------------------------------------------------- |
| 请求状态     | `InputBatch` 行号 = batch 顺序，另需 `CachedRequestState` | `RequestState` 固定槽位 + `idx_mapping` | 镜头 C：搬动约 544 KB → 0                                             |
| 输入准备     | CPU NumPy 逐 token 计算，再 H2D                           | GPU Triton kernel gather                | 镜头 A：CPU 生成 4.1 万个数 → 只算 `idx_mapping` 和 `query_start_loc` |
| 块表         | 每步上传本步请求的整行                                    | 常驻 GPU，只传新增块 ID                 | 镜头 B：256 KB/步 → 几十字节                                          |
| 每步上传合计 | 32 路满载时 257 – 544 KB                                  | 0.4 – 2.5 KB                            | 全程 116 MB → 0.27 MB                                                 |
| 上一步 token | -1 占位 + scatter                                         | kernel 按槽号读取                       | 少一次 CPU 索引构造和 H2D                                             |
| 同步点       | 输入 barrier；投机解码每步等接受数                        | 无                                      | 官方：GLM-4.7 + MTP 的 TPOT −6.3%                                     |
| 采样         | softmax + 指数噪声，两张 [B, V] 临时表                    | Gumbel-Max，噪声在寄存器里              | 镜头 B：37 MB → 0                                                     |
| 模型扩展     | 直接写进 Runner                                           | `ModelState` 接口                       | M-RoPE、多模态 embedding 各有归属                                     |
| 官方吞吐     | 16K tok/s                                                 | 25K tok/s                               | Qwen3-0.6B / 1×GB200，+56%                                            |

一句话：MRV1 用 CPU 维护一张“既是状态又是输入”的表，MRV2 让状态有固定地址并常驻 GPU，CPU 只负责告诉 GPU 这一步要哪些槽、按什么顺序。

## 九、版本沿革

`v0.18.x` 时 MRV2 还要用 `VLLM_USE_V2_MODEL_RUNNER=1` 手动开启，那时不支持线性注意力、LoRA、EPLB、logits processors 等功能。`v0.22` 至 `v0.25` 默认范围逐步扩大，[`v0.29`][release29] 起只要配置里没有不支持的功能就默认使用 MRV2，`v0.33.0` 仍保留回退逻辑（[选择逻辑][stable-runner]），[`main` 删除了 MRV1][remove-mrv1]。

## 附录：计算口径与对上一篇的修正

<details markdown="1">
<summary>展开计算口径</summary>

- **调度推演**：FCFS；每步先排 running 队列（未完成 prefill 的请求继续 prefill，其余 decode 1 个 token），再在 `len(running) < 32` 且预算有剩余时接入 waiting 请求；prompt 最后一个位置算完就采出首个 token；生成满 200 个 token 后，下一步退出。共 428 步。
- **MRV1 每步上传**：`commit_block_table(R)` 上传 R × 2,048 × 4 B；`slot_mapping` N × 8 B；`input_ids` N × 4 B；M-RoPE positions 3 × N × 8 B；`query_start_loc`、`seq_lens` 整个 buffer 共 260 B；`discard_request_mask` R × 1 B。其中 R 是本步请求数，N 是本步 token 数。
- **MRV2 每步上传**：`idx_mapping` R × 8 B；`query_start_loc` 33 × 4 B；块表增量 = 新块数 × 4 B + 每行 12 B 的写入元数据。经 UVA 读取的 prompt token（4 B）和 M-RoPE 位置（3 × 4 B）单独统计。
- **不计入**：两代都要做的一次性工作，例如新请求的 prompt 写入，以及只在 batch 变化时才上传的采样参数。
- **单位**：KB = 1,024 B，MB = 1,024 KB。
- **视频 token 估算**：Qwen3-VL-8B 处理后 64 帧、448×448 时，视觉占位约 `(64/2) × (448/16/2)² = 6,272` 个 token，再加上模板、时间戳和文本，取整为 7,000。[Checkpoint 配置][qwen-config] · [视觉网格计算][qwen-code]

</details>

<details markdown="1">
<summary>展开对上一篇第 5.6 节的两处修正</summary>

1. **Step 40+ 不会有 R33 进来。** `max_num_seqs = 32` 时，32 个槽在第 27 步就占满了，R33 要等 R1 在第 200 步生成完才能进入（第 201 步）。上一篇写的“R1–R32 decode + R33、R34 prefill”同时有 34 个活跃请求，与这个上限矛盾。
2. **约 30 倍吞吐的结论不成立。** 原文估算 Static Batching 要“2 批 × (7,000 + 200) ≈ 14,400 步”，把 7,000 个 prefill token 当成了 7,000 次 forward。实际上一个 prompt 的 prefill 只需一次或几次（分块）forward，所以两种 batching 的步数差远没有 30 倍。

</details>
